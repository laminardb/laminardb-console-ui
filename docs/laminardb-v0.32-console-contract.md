This is the implementation contract used by this console. It is deliberately pinned to an engine commit: the `0.32.0` workspace version is not, by itself, a sufficiently precise compatibility boundary while `main` continues to change.

## Compatibility summary

The console supports the HTTP and browser WebSocket surface at the exact commit above. It treats all Rust `u64` values and all exact-integer Arrow JSON fields losslessly, warns when `/health` reports a version other than `0.32.0`, and does not infer compatibility from that version warning alone.

There is no engine build-SHA field in `HealthResponse`, so a browser cannot prove that a connected `0.32.0` binary is this exact commit. Operators must pin the server artifact outside this protocol. A differently built `0.32.0`, a feature-reduced binary, custom connectors, or a later `main` commit is best-effort and may require a new contract review.

| Contract | Behaviour | Source file and Rust type/function |
| --- | --- | --- |
| Public probes | `/health`, `/ready`, and `/metrics` are unauthenticated. The console deliberately sends no bearer header. | [`router::build_router`][router] |

## JSON and SQL contract

### HTTP SQL responses

`SqlResponse` has `result_type` and these variant fields:

| `ExecuteResult` | HTTP fields | Source file and Rust type/function |
| --- | --- | --- |
| `Ddl(DdlInfo)` | `result_type = statement_type`, `object_name` | [`ExecuteResult`, `DdlInfo`][execute-result], [`catalog::execute_sql`][catalog-http] |
| `RowsAffected(u64)` | `result_type="rows_affected"`, `rows_affected` | [`ExecuteResult`][execute-result], [`catalog::execute_sql`][catalog-http] |
| `Metadata(RecordBatch)` | `result_type="metadata"`, `data` | [`ExecuteResult`][execute-result], [`catalog::execute_sql`][catalog-http] |
| `Query(QueryHandle)` | `result_type="query"`, `data`, and `truncated=true` only when capped/timed out | [`catalog::SqlResponse`, `MAX_SQL_RESULT_ROWS`, `SQL_RESULT_TIMEOUT`][catalog-http] |
| `Ddl(DdlInfo)` with `topology_operation` (cluster, Running) | HTTP **`202`**, `result_type="TOPOLOGY MIGRATION"`, `object_name` = canonical object, `topology_operation: TopologyAdmissionStatus`. Each statement becomes its own single-statement migration with a server-generated identity; multi-statement SQL is split and run one at a time. The receipt is an admission, not an applied change. | [`catalog::execute_sql`][catalog-http], [`submit_cluster_topology_sql`][db-topology-submission] |

HTTP query collection stops at 1,000 rows or after 5 seconds and returns the collected prefix with `truncated=true`. HTTP SQL explicitly rejects both direct `SUBSCRIBE` and `DECLARE CURSOR FOR SUBSCRIBE`; those belong to pgwire. [`LaminarDB::execute`][db-mod]

Arrow JSON uses explicit `null` fields. `Int64`, `UInt64`, and decimal values are encoded as decimal strings; non-finite floats are strings. This avoids JavaScript precision loss in tabular SQL/checkpoint output. Direct serde control-plane `u64`s can still be JSON numbers, so the console uses lossless JSON parsing before normalising them to decimal strings. [`json_encoding::exact_json_encoder_options`][json-encoding]

### AI SQL

The eight registered marker UDFs are `ai_classify -> Utf8`, `ai_sentiment -> Float64`, `ai_embed -> List<Float32>`, and `ai_extract`, `ai_complete`, `ai_summarize`, `ai_translate`, `ai_gen -> Utf8`. ## Cluster lifecycle and assignment ABI

`NodeState` has exactly `Joining`, `Active`, `Suspected`, `Draining`, and `Left`. `NodeInfo` is `{id: NodeId(u64), name, rpc_address, state, metadata, last_heartbeat_ms}` and `NodeMetadata` is `{cores, memory_bytes, failure_domain, tags, version}`. It has no Raft fields and no owned-partition list. Only `Active` nodes are assignable. [`NodeState`, `NodeMetadata`, `NodeInfo`, `assignable_node_ids`][discovery]

`AssignmentSnapshot` is:

```text
version: u64
partitioning_abi_version: u16
vnodes: BTreeMap<u32, NodeId>
participants: Vec<CheckpointParticipant>
updated_at_ms: i64
draining: bool
drain_transition: Option<AssignmentDrainTransition>
```

The drain transition binds predecessor and target `CheckpointAssignmentFence`s plus `LeaderProof`; participant identities include node ID and boot incarnation. The partitioning ABI constant is `2`. Key groups are a typed range `1..=65535`; the common default is 256, but `[server].key_groups` is mode-neutral and configurable, so the console derives cardinality from the returned map rather than assuming 256. [`AssignmentSnapshot`][assignment-snapshot], [`AssignmentDrainTransition`, `CheckpointAssignmentFence`, `CheckpointParticipant`, `LeaderProof`][checkpoint-assignment], [`KeyGroupCount`, `PARTITIONING_ABI_VERSION`, `DEFAULT_KEY_GROUP_COUNT`][vnode]

Direct serde control-plane node, assignment, fence, and term IDs may exceed JavaScript's safe integer range. They are parsed losslessly and rendered as decimal strings by this console.

Pipeline `start`/`stop` acts locally first. In cluster mode, omitting `local=true` sends concurrent fire-and-forget requests to known peers; peer errors are logged and do not fail the initiating response. A successful response proves only the local operation, not cluster-wide convergence. [`fan_out_pipeline_control`][cluster-admin]

The `/cluster`, `/cluster/nodes`, `/cluster/vnodes`, `/cluster/leader` and `/cluster/checkpoints` wire shapes are unchanged since the 0.30 review.

### Rescaling, drain and recovery

There is **no rescale API**. Vnodes (`server.key_groups`) are fixed per deployment; owners are stable `node_id` processes assigned by unweighted rendezvous hashing. Scale out by starting a node with a new stable `node_id` (added after the rebalance debounce and a handoff checkpoint). Scale in with SIGTERM: the node reports `Draining` and waits up to `server.drain_timeout` (default `checkpoint.timeout` + 30 s, and at least `checkpoint.timeout`) for its vnodes to move; on timeout it exits fenced with `graceful drain incomplete` and survivors recover its vnodes from the last committed checkpoint. A process counts its own vnodes in `placement_owned_vnodes`. While `ClusterTopologyStatus.live_migration` is set the complete owner map is frozen and only same-slot replacement of a failed process is admitted. [`server README: rescaling`][server-readme], [`ServerSection::drain_timeout`][server-config], [`placement metrics`][placement-metrics]

## Cluster topology migrations

A Running cluster changes its source/stream/sink graph through durable, payload-bound migration requests admitted between two checkpoints. Every required owner process certifies the candidate, the cluster pauses at one reconciled old-topology checkpoint cut, the target catalog commits atomically, and intake resumes after an owner-complete Release.

### Phases

`state` is internally tagged by `phase`:

| Phase | Meaning |
| --- | --- |
| `planned` | Request reserved; graph and catalog still belong to the parent. |
| `preparing` | Participants certify the exact candidate; intake stays open. |
| `quiescing` | One old-topology checkpoint barrier and sink settlement are in progress. |
| `cut_prepared` | Every process applied the cut and holds intake. |
| `committed` | Catalog and migration root committed. **Irreversible**; cannot abort; the target is not yet running and output/intake are not authorized. |
| `activating` | Installation receipts for the target runtime are being collected with intake held. |
| `active` | Participant-complete Release committed (`activation.release` present). Terminal success; each node's local activation is observed separately through its own `locally_active_version`. |
| `aborted {reason}` | Only before commit. `reason`: `requested`, `leader_changed`, `recovery`, `checkpoint_aborted`. |

A phase that makes no progress for 180 s triggers coordinated recovery automatically.

### Errors and retries

Topology write routes (submit, adopt, and topology failures on `/api/v1/sql`) return `{error, code}`; other routes return `ErrorBody`. Codes: `LDB-6060` invalid, `6061` parent conflict / unknown operation, `6062` fenced, `6063` protocol unsupported (including runtime DDL before adoption), `6064` contended/timeout/busy, `6065` authority failed, `6066` change unsupported. Status mapping: conflict `409`; invalid/SQL `400`; protocol/unsupported `422`; planning busy `429`; contended/read or planning timeout `504`; other topology errors and shutdown `503`; body over the limit `413`; JSON rejection (unknown field, nil UUID, version 0) `422`. `429` and `504` carry `Retry-After: 1`. [`topology_write_error`][topology-submission-http], [`error codes`][error-codes]

After a `503`/`504` (or a network failure) the admission outcome is uncertain. The console keeps the same operation identity and payload, tracks the identity's durable status, and offers a retry that reuses both. An uncertain SQL migration reports `"…; topology operation <uuid> may be admitted; query status and retry the same identity"`; the console extracts that identity because the CORS allow-list hides the response header. [`DbError::TopologySubmission`][db-error]

### Operator workflow implemented by the console

1. **Adopt** once when `catalog.state` is `legacy_sealed`, after every node runs the 0.32 binary: post the sealed `manifest`, the deployment UUID (operator-supplied) and `coordinated_upgrade_complete: true`, behind an explicit confirmation.
2. **Validate** (optional, effect-free, local to the answering node) against `committed_version`; the console renders each object's transition and initialization and the activation requirements still outstanding. Validation is rejected while process functions are bound.
3. **Submit** with a fresh UUID behind a confirmation; reuse that UUID for any retry of the identical payload (reusing it for a different payload is a `409`). Admission is a `409` while the journal is full, while another topology operation, a recovery, or an assignment drain/handoff is unresolved, or when the expected parent no longer matches; a checkpoint in flight is `504` (contended) and retryable with the same plan. [`topology_admission`][topology-admission-lease]
4. **Track** `GET /operations/{id}` until `active` or `aborted`, then compare `locally_active_version` with the committed target on the connected node. The console does not call `/prepare`.

Single-statement migrations can also come from `/api/v1/sql`; their receipts are tracked the same way. Use a request for atomic multi-statement changes.

### Carried forward from the 0.30 review

The pre-0.30 console was not a safe description of this contract. The 0.30 review changed it as follows:

- Uses port 8080, the current server default, rather than README port 8000.
- Removes the nonexistent `/api/v1/queries` dependency and static connector capability claims.
- Handles `Stopped` as a reachable `503 /health`, distinguishes readiness, and probes a protected route so a wrong token cannot appear connected.
- Sends no bearer token to public probes, keeps the console token in session storage, migrates/removes the old persistent token, validates base URLs, and uses query-token auth only for WebSocket upgrades.
- Parses exact integers losslessly; cluster IDs, assignment versions, checkpoint fields, SQL integer/decimal cells, and subscription cursors are not rounded by JavaScript.
- Uses the returned assignment map and ABI instead of assuming 256 vnodes; renders the actual five node lifecycle states and exact assignment participant/drain fields; removes Raft/partition-lease inventions.
- Makes pipeline cluster fan-out limitations explicit and requires confirmation for lifecycle mutations.
- Replaces the old WebSocket request/response assumptions with the server's one-target-per-socket, server-only application protocol; validates all four outbound frames, bounds retained UI rows, and resumes only after explicit operator action from a progress epoch.
- Enables the feature branch's checkpoint-committed cluster subscriptions for stream targets while leaving cluster MVs unavailable. Durable replay deduplication uses generation/partition/partition-sequence/row-offset identity, the result view exposes partition metadata, and the UI explicitly rejects any inference of cross-partition order.
- Separates HTTP SQL from WebSocket subscriptions and changes local versus cluster tail/replay guidance instead of treating them as one storage model.
- Treats checkpoint status as one current row, handles structured checkpoint failures, uses real checkpoint/state metrics, and documents automatic rather than manual restore.
- Drives connector choices from `/api/v1/connectors`, redacts secret-looking connector properties and SQL in display surfaces, and avoids claiming delivery guarantees the endpoint does not carry.
- Uses only registered metric names, tolerates valid Prometheus non-finite values without charting them, and keeps raw metric discovery available.
- Adds keyboard/focus-safe dialogs, semantic tables/status regions, visible focus, reduced motion, responsive layout, accessible chart summaries, automated protocol fixtures, and axe smoke tests.

## Verification gaps and unsupported boundaries

- The protocol and UI fixtures are pinned to the `main` SHA, but this console review did not run a multi-node cluster, a live topology migration, or an external Kafka, NATS, PostgreSQL, MongoDB, Delta, Iceberg, OTel, or WebSocket service matrix. Topology and connector behaviour was traced through the production implementation and its HTTP, topology-planning/submission, cluster/Iceberg/CDC soak and end-to-end suites; topology wire shapes are covered by console fixtures derived from those types.
- The console cannot read the deployment UUID needed for legacy adoption; operators must supply it from the checkpoint store. Topology activation evidence is per process, so `locally_active_version` describes only the node the console is connected to.
- Kafka reader lag is the only per-instance connector metric. Other connector families are process-wide and unlabelled; a second same-type connector on one node is not exported.
- The console cannot verify a server's commit SHA because the server exposes only the semantic version. Artifact/deployment attestation remains an operator responsibility.
- Feature-reduced or custom-connector server builds can return a different connector catalog and metric set. The UI renders discovery dynamically but cannot infer custom delivery contracts because `ConnectorInfo` does not expose them.
- Cluster diagnostics are intentionally not rendered or stored by this browser console: they sit outside console CORS, may use a separate high-sensitivity token, and expose process authority evidence. Use an authorised loopback diagnostic client and the schema-versioned envelopes.
- Pgwire was reviewed for the cross-transport resumption question but is not exercised by a browser SPA. This console does not act as a PostgreSQL client.
- Browser WebSocket APIs do not reveal failed-upgrade bodies/status, so detailed `400`/`404`/`409`/`410`/`500`/`503` diagnostics require server logs or a non-browser client. The catalog REST shape does not expose a subscription-capability flag, so the console can exclude cluster MVs but must let the engine perform exact stream-plan admission.
- Cluster subscription support is intentionally limited to named non-windowed managed keyed aggregate streams. Stateless streams, global aggregates, raw joins, windows, MVs, arbitrary UDAFs, live relay, durable named-consumer acknowledgement, emitted/accepted resume tokens, and global total order are unsupported and are not emulated by the console.
- Manual `RESTORE FROM CHECKPOINT`, live single-node source/sink/table topology DDL, cluster migration of materialized views/tables/lookups, a rescale API, a topology operation list endpoint, delivery-contract discovery through REST, checkpoint history, and state-tier/budget-limit metrics remain unsupported.
